\subsection{Data Logging and PWA Communication}
\label{sec:ch3-pwa-monitoring}

The monitoring system was implemented as a PWA connected to Firebase. The PWA
was not placed in the protection path; the ESP32-S3 still made relay decisions
locally. The PWA instead provided live measurements, protection status, event
history, CSV download, labeling support, and review of waveform-derived
features. This separation allowed the prototype to remain protective during
network loss while still supporting data collection and analysis.

\textit{Figure~\ref{fig:ch3-pwa-block}} shows the PWA and Firebase data path.
\begin{figure}[H]
  \centering
  \begin{tikzpicture}
    \node[anchor=south west,inner sep=0] (img) at (0,0)
      {\includegraphics[width=0.88\textwidth]{ch3/figure_3.12.png}};
  \end{tikzpicture}
  \caption{PWA block diagram and Firebase data path.}
  \label{fig:ch3-pwa-block}
\end{figure}

\textit{Figure~\ref{fig:ch3-pwa-block}} shows the communication path 
among the ESP32-S3 firmware, Firebase Realtime Database, and the 
browser-based PWA. The firmware serves as the main decision-making 
unit by acquiring sensor data, evaluating protection conditions, and 
publishing selected voltage, current, temperature, fault-state, and 
logging data to Firebase.

The PWA subscribes to these Firebase paths to display live measurements, 
time-series charts, fault history, and logging status. It may also 
write operator commands, such as relay control or fault clearing, but 
these commands are still validated and executed by the ESP32-S3. This 
setup improves remote monitoring and data recording while keeping 
time-critical protection actions, such as overload, arc-fault, and 
socket-heating response, local to the device and less dependent on 
browser availability or network delay [55], [56].
